01OVERVIEW

이 스택이란?

AI 엔지니어링은 하나의 기술이 아니라 다섯 개 레이어로 쌓인 스택입니다. 각 레이어는 모델로부터 한 단계씩 더 바깥쪽 시스템을 다룹니다.

Graph — 여러 에이전트/작업 사이의 관계를 설계
└ Loop — 하나의 작업이 스스로 반복·종료되도록 설계
└ Harness — 실행 환경과 권한, 완료 기준을 설계
└ Context — 한 턴에 모델이 보는 정보를 설계
└ Prompt — 한 번의 메시지를 설계

중요한 원칙: 위 레이어로 올라간다고 아래 레이어가 필요 없어지는 게 아닙니다. 그래프는 여러 루프를 담고, 루프는 하나의 하네스 위에서 돌고, 하네스는 컨텍스트를 관리하고, 컨텍스트는 결국 프롬프트로 조립됩니다. 실제 앱 서비스 대부분은 1~3단계만으로 충분하며, 5단계까지 필요한 건 사용자 개입 없이 장시간 자율적으로 처리해야 하는 기능을 만들 때뿐입니다.

02SCENARIO

예시 시나리오: "일정관리 앱에 AI 비서 기능 넣기"

아래 모든 레이어는 하나의 앱 서비스 개발 시나리오를 끝까지 관통시켜 설명합니다.

우리 팀은 캘린더 앱을 만들고 있고, "내일 오후 3시에 김대리랑 회의 잡아줘" 같은 자연어 한 줄로 일정을 잡아주는 AI 비서 기능을 이 앱에 추가하려 합니다.

이 기능이 초기 MVP에서 완성형 자동화 기능으로 성장하는 과정을 5단계로 따라가 봅니다.

01PROMPT ENGINEERING

한 번의 요청을 설계한다

설명

모델에게 단 한 번의 호출에서 무엇을, 어떻게 말할지 설계하는 가장 기본 레이어입니다. 모델은 이전 대화를 기억하지 못하므로 역할, 지시사항, 예시, 출력 형식을 그 한 번의 메시지 안에 모두 담아야 합니다. 앱 개발 관점에서는 가장 적은 개발 리소스로 가장 빠르게 기능을 검증할 수 있는 단계입니다.

사용법
  • 역할·톤 고정: "당신은 일정 관리 비서입니다"로 응답 스타일 통일
  • Few-shot 예시: "내일 3시 회의 잡아줘" → 파싱 결과 예시 2~3개 제공
  • 출력 형식 강제: 앱 프론트엔드가 바로 쓸 수 있도록 JSON 스키마({title, start, end, attendees})로 응답 고정
  • Chain-of-Thought: "먼저 날짜·시간·참석자를 각각 추출한 뒤 JSON으로 정리하라"
사례 (앱 서비스 개발)

캘린더 앱 개발팀이 자연어 → 일정 정보 추출 프롬프트를 작성해 API 응답으로 붙입니다. "내일 오후 3시 김대리랑 회의"를 입력하면 {title: "김대리 회의", start: "2026-09-08T15:00"} 형태로 파싱됩니다. 데모에서는 잘 작동하지만, 곧 문제가 생깁니다 — 사용자가 이미 그 시간에 다른 일정이 있는지, 김대리가 누구인지(연락처에 여러 명일 수 있음) 모델은 전혀 알지 못합니다.

02CONTEXT ENGINEERING

무엇을 보여줄지 설계한다

설명

프롬프트를 넘어, 모델이 이번 턴에 실제로 보게 될 모든 정보를 설계하는 레이어입니다. 핵심은 "무엇을 더할까"가 아니라 "무엇을 정확히 골라 넣을까"입니다. 앱 서비스에서는 사용자 데이터·기기 상태·앱 내 다른 화면 맥락까지 컨텍스트 설계 대상이 됩니다.

사용법
  • 개인화 데이터 주입: 사용자의 기존 일정, 자주 만나는 연락처, 선호 회의 시간대
  • 모호성 해소 정보 포함: 연락처에 동명이인이 있으면 최근 통화·메시지 빈도로 우선순위 후보 추림
  • 관련 없는 정보 제거: 1년 전 일정, 삭제된 연락처 등은 컨텍스트에서 배제해 토큰 낭비·혼선 방지
  • 디바이스/앱 상태 반영: 현재 보고 있는 화면(주간 뷰/월간 뷰)에 맞춰 응답 형식 조정
사례 (앱 서비스 개발)

개발팀이 요청을 처리하기 전, 오늘 기준 앞뒤 2주 일정 + 연락처에서 "김대리"와 일치하는 후보 목록 + 사용자의 평소 회의 선호 시간을 컨텍스트에 포함시킵니다. 이제 모델은 "김대리가 이미 그 시간에 다른 미팅이 잡혀 있다"거나 "김대리라는 이름이 2명이라 확인이 필요하다"는 것까지 알고 응답합니다. 하지만 여전히 실제로 캘린더에 일정을 등록하거나 상대방에게 초대를 보내는 건 못 합니다.

03HARNESS ENGINEERING

실행 환경과 권한, 완료 기준을 설계한다

설명

모델을 실제로 무언가를 실행할 수 있는 환경에 연결하는 레이어입니다. 앱의 실제 API, 알림 시스템, 권한 체계, 그리고 결과가 맞는지 검증하는 장치까지 포함한 "모델 주변의 발판"을 설계합니다.

사용법
  • 도구(Tool) 범위 설계: "캘린더 조회"는 자유롭게, "타인 초대 발송"은 확인 절차 후에만 허용
  • 권한 경계: 회사 캘린더 앱이라면 팀 캘린더 조회는 허용하되 임원 캘린더 수정은 금지
  • 검증기 분리: 일정 등록 결과가 실제로 시간 충돌 없이 저장됐는지 별도 로직으로 채점
  • 실패 복구 경로: 캘린더 API 호출 실패 시 사용자에게 알리고 재시도하는 규칙 정의
사례 (앱 서비스 개발)

개발팀이 AI 비서에게 "캘린더 조회 API", "일정 생성 API", "알림 발송 API"를 도구로 연결합니다. 단, 참석자가 3명 이상이거나 외부 인원이 포함된 일정은 자동 발송 대신 "사용자 확인 후 발송"으로 권한을 제한합니다. 별도의 검증 로직이 "시간 충돌 여부"를 앱 DB에서 재확인합니다. 이제 AI 비서는 실제로 일정을 등록할 수 있지만, 아직은 사용자가 앱을 열어 요청을 입력할 때만 동작합니다.

04LOOP ENGINEERING

시스템이 스스로 반복하도록 설계한다

설명

설계의 초점이 "이번 요청에 뭐라고 답할까"에서 "목표와 종료 조건을 미리 정해두고, 시스템이 관찰(observe)→실행(act)→검증(verify)→복구(recover)를 스스로 반복하게 만들 것"으로 옮겨갑니다. 사용자가 매번 개입하지 않아도 하나의 작업이 끝까지 처리됩니다.

사용법
  • 목표·종료 조건 명시: "빈 시간대를 찾고, 참석자 전원이 수락하거나 3회 재제안 후 종료"
  • 관찰-실행-검증 사이클: 제안한 시간에 상대가 거절하면, 그 결과를 반영해 다음 후보 시간을 자동 재탐색
  • 컨텍스트 관리: 재탐색이 길어질수록 이전 실패 이유를 요약해 누적, 전체 기록을 다 넣지 않음
  • 채점기 재사용: harness 단계의 시간 충돌 검증 로직을 루프의 매 반복마다 재사용
사례 (앱 서비스 개발)

사용자가 "다음 주 안에 팀 전체랑 회식 자리 잡아줘"라고 한 번만 요청하면, AI 비서가 팀원 전체의 빈 시간 탐색 → 후보 3개 제안 → 각자에게 알림 발송 → 응답 수집 → 과반수가 되는 시간으로 자동 확정(또는 안 되면 재탐색)을 사용자 개입 없이 반복합니다. 앱은 이제 "회식 잡아줘" 한 마디로 하루 이상 걸리는 조율까지 자동으로 처리합니다. 하지만 이 기능이 "회식 잡기", "출장 일정 조율", "화상회의 세팅" 등 여러 종류로 늘어나면 — 각기 다른 전문 로직이 서로 얽히기 시작합니다.

05GRAPH ENGINEERING

여러 작업과 실행 사이의 관계를 설계한다

설명

하나의 루프로는 부족해지는 시점, 즉 여러 전문 에이전트(또는 여러 루프)가 협업하는 구조를 설계하는 레이어입니다. 다음 4가지 요소로 구성됩니다.

현상이름앱 서비스 관점 의미
계획과 수행의 분리Node회식 조율 담당, 출장 조율 담당, 화상회의 세팅 담당처럼 역할별 독립 처리 단위
무엇을 기다릴지Edge"참석자 5명 이상이면 회식 조율 Node로", "해외 출장이면 출장 Node로" 같은 라우팅 조건
진행 상황 보존State어떤 요청이든 공유하는 "이 사용자의 이번 주 일정 현황" 같은 공통 맥락
완료 판단Verifier개별 Node 결과뿐 아니라, 최종적으로 사용자 캘린더에 충돌 없이 반영됐는지 최종 검사
사용법
  • Node 분리: 요청 분류(triage) → 회식/출장/화상회의 등 전문 Node로 위임
  • Edge(라우팅) 설계: 참석자 규모, 외부 인원 포함 여부, 예산 승인 필요 여부에 따라 다음 Node 결정
  • State 공유: 모든 Node가 같은 "사용자 주간 일정 State"를 참조해 서로 다른 Node가 같은 시간대에 중복 예약하지 않도록 방지
  • Verifier 배치: 각 Node 출력과 별개로, 그래프 전체 완료 시점에 캘린더 최종 상태를 한 번 더 검증
  • 사람 승인 Edge: 예산이 드는 출장·행사 예약은 자동 확정 대신 관리자 승인 Node로 흐르게 설계
사례 (앱 서비스 개발)

사용자가 "다음 달 부산 워크숍 잡아줘"라고 요청하면 분류 Node가 이를 "출장/행사" 유형으로 라우팅합니다. 출장 조율 Node는 항공권·숙소 API를 조회하고, 일정 조율 Node는 참석자 빈 시간을 맞추고, 예산이 일정 금액을 넘으면 관리자 승인 Node로 흐릅니다(Edge). 모든 Node는 같은 "이번 워크숍 State"를 공유해 중복 예약을 막고, 마지막에 Verifier가 항공권·숙소·일정이 모두 충돌 없이 확정됐는지 검사한 뒤에야 사용자에게 최종 알림을 보냅니다. 이것이 캘린더 앱의 AI 비서가 "회의 하나 잡는 기능"에서 "여러 팀의 복잡한 일정·예산·승인까지 조율하는 기능"으로 성장한 최종 형태입니다.

08SUMMARY

한눈에 보는 비교 (앱 서비스 개발 기준)

레이어설계 단위핵심 질문앱 개발 관점 산출물이 단계만으론 부족해지는 시점
Prompt한 번의 메시지어떻게 말할까?자연어 → 구조화 응답 프롬프트사용자 데이터가 필요할 때
Context한 턴에 보이는 정보무엇을 골라 보여줄까?개인화 데이터 주입 로직실제 액션 실행이 필요할 때
Harness실행 환경 전체어디까지 권한을 줄까?API 연동 + 권한 경계 + 검증 로직사용자가 매번 트리거해야 할 때
Loop작업 하나 전체언제 멈출까?자동 재시도·조율 로직기능 종류가 여러 개로 늘어날 때
Graph작업들 사이 관계누가 누구에게 넘길까?멀티 에이전트 라우팅·승인 플로우(대부분의 앱 기능은 여기까지 안 가도 됨)
09CHECKLIST

실무 체크리스트

새 AI 기능을 앱에 추가할 때, 아래 순서로 자문해보세요.

  • 1Prompt: 이 기능이 "한 번의 응답"으로 끝나는가? → 그렇다면 여기서 멈춰도 충분
  • 2Context: 응답 품질이 사용자별 데이터 부족 때문에 떨어지는가? → Context 레이어 보강
  • 3Harness: 실제로 뭔가를 실행(등록/발송/결제 등)해야 하는가? → 도구 연동과 권한 설계 필요
  • 4Loop: 사용자가 결과가 나올 때까지 앱 앞에서 기다려야 하는가? → 자율 반복·재시도 로직 필요
  • 5Graph: 서로 다른 전문성이 필요한 하위 작업이 3개 이상 얽혀 있는가? → 멀티 에이전트 구조 검토

대부분의 앱 기능은 1~3단계에서 멈춥니다. 5단계까지 필요한 건 "사람 개입 없이 장시간, 여러 하위 작업을 스스로 조율해야 할 때" 뿐입니다.
